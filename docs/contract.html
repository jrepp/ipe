The integration contract

You provide the facts.
IPE evaluates the rules.

IPE is a policy decision component. Your application supplies the rules and request data, receives a decision or an error, and decides whether to carry out the action.

Current behavior and design targets, explained separately

What goes in, what comes out

  1. 1. Policies + factsLoad rules and describe the requested action.
  2. 2. EvaluationFind policies for the resource type and run their bytecode.
  3. 3. Decision or errorReturn Allow, Deny, or an evaluation failure.
  4. 4. Application actionYour application permits or blocks the operation.

This page describes the Rust library. It does not define an HTTP endpoint or a JSON request format.

What you supply

The policy set. Rules loaded into the selected evaluation API. The core PolicyDB accepts compiled bytecode, field mappings, names, and the resource types each policy applies to.

The resource. What is being acted on: for example, a deployment, with attributes such as environment and approval count.

The action. What someone wants to do: for example, deploy to production.

The request. Who is asking, when, and any relevant request metadata.

These three groups form the Resource–Action–Request context, or RAR. In the current Rust API, resource types use numeric ResourceTypeId values.

What you receive

Allow. The selected evaluator accepted the request under its policy-combination rules.

Deny. The selected evaluator rejected the request, including when no policies were found for the resource type.

Error. Evaluation could not complete, for example because a required field or bytecode constant was missing. The caller must handle this separately from a policy denial.

A successful Rust result contains Decision { kind, reason, matched_policies }. The reason is optional, and the policy-name list is not a complete audit trace. A failed result is Err(Error::EvaluationError(...)).

An everyday example

Suppose a deployment requires two approvals and must also pass a change-freeze check. The approval rule allows it, but the freeze rule denies it.

PolicyEngine returns Deny. PolicyDataStore currently returns Allow. This example assumes correctly constructed bytecode; the source compiler has the limitations described below.

Your application is still responsible for stopping the deployment. IPE does not perform or reverse the deployment itself.

What your application owns

  • Trustworthy facts. Authenticate the caller and supply accurate, appropriately validated attributes.
  • Policy administration. Decide who can change rules, how rules are reviewed, and which resource types they cover.
  • Error handling. Choose an explicit failure policy. For an authorization integration, block the action when evaluation fails.
  • Enforcement and records. Apply the decision and record the context, policy version, outcome, and relevant diagnostics.

These are integration responsibilities. An Allow result does not authenticate a user, grant permissions in another system, or execute a business operation.

Current limits you need to know

Source-to-decision enforcement is incomplete. The current compiler skips trigger conditions and ends a requires policy with a fixed Return(true). The interpreter returns that fixed value. A false condition can therefore still produce Allow.

Parsing or compiling a policy successfully is not evidence that its rules are enforced correctly. Validate the complete decision path before using source policies to control access.

Evidence: PolicyCompiler::compile and Interpreter::evaluate. The AST explorer shows parsed structure. The dashboard measures hand-built interpreter bytecode; neither proves the compiler path is correct.

What does “same input, same result” mean?

Deterministic and side-effect-free evaluation is a stated requirement. Reproducibility needs the same policy version, evaluator, context, and any external approval or relationship data. Changing the timestamp or external facts changes the input. This summary does not certify every execution path against that requirement.

Targets are not guarantees

The requirements aim for interpreter p99 latency below 50 microseconds and at least 100,000 evaluations per second per core. “p99” means 99% of measured evaluations finish within that time.

Those are design targets, not a service-level agreement. The dashboard reports limited local measurements. JIT latency, production workload behavior, uninterrupted updates, and consistency across execution paths need their own validation.

See REQ-EVAL-001–006, REQ-PERF-001–007, and REQ-REL-001–011 for the formal requirements.

Scope: the current Rust implementation. Review this summary when changing decision combination, compiler returns, error handling, or the public context and decision types.
