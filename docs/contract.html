Reference / Contract

Contract

IPE evaluates policies and returns a decision or an error. Your application enforces the decision.

Integrate · 1 of 3Scope: Rust library

Inputs and results

You pass
Policies
The rules for each resource type
Resource
The affected object, with its type and attributes
Action
The operation and its target
Request
Information about the caller and request
You get
Allow
The policy result permits the action
Deny
The policy result rejects the action
Error
Evaluation fails, for example when a required field is absent

The Resource–Action–Request (RAR) context contains the data for one evaluation. Resource types use numeric ResourceTypeId values.

Ok(Decision { kind, reason, matched_policies })
Err(Error::EvaluationError(..))

The reason is optional. A Deny result can omit policy names.

Decision rules

Both APIs select policies by resource type. Their rules differ when policies return conflicting results.

Policy resultsPolicyEnginePolicyDataStore
No policies for the resource typeDenyDeny
All allowAllowAllow
All denyDenyDeny
Some allow, some denyDenyAllow
Any evaluation failsErrorError

Source: PolicyEngine::evaluate. (PolicyDataStore was removed in #36; the legacy engine stack was deleted in the legacy-cluster disposition.)

Application responsibilities

  • Your application authenticates the caller and supplies the request data.
  • Your application controls who can change policies.
  • Your application handles evaluation errors.
  • Your application permits or blocks the action and records the result.

Current limits

  • The compiler does not evaluate trigger conditions.
  • The compiler ends a requires policy with Return(true).
  • The interpreter returns the value in that instruction. A false condition can therefore produce Allow.

Sources: PolicyCompiler::compile and Interpreter::evaluate (both removed with the legacy engine stack).

Requirements

The p99 latency is the time within which 99% of measured evaluations finish.

RequirementTarget
Interpreter p99 latencyBelow 50 microseconds per evaluation
Interpreter throughputAt least 100,000 evaluations per second per core
Repeated evaluationThe same policies and inputs produce the same result without side effects

The performance page reports measurements for three interpreter workloads. It does not measure JIT compilation or production traffic.

Source: REQ-EVAL-005–006, REQ-PERF-001, and REQ-PERF-006.
