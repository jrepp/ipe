Reference / Contract

Contract

The runtime evaluates policies against expiring runtime facts and returns allow, deny, or indeterminate. Your application enforces the decision.

Integrate · 1 of 3Scope: v2 runtime API

Inputs and results

You pass
Input
The request JSON the evaluating workload attests, validated against the scope's input schema
Runtime facts
Typed values in scoped collections, every one carrying a finite TTL
Policy documents
Versioned language-2 rules with typed policy.* parameters and provenance
Bootstrap policies
Policy sources fixed in the bootstrap configuration
You get
Allow
Every applicable policy allowed and no evidence deadline passed
Deny
Some policy denied — a deny overrides everything else
Indeterminate
Evidence was missing, expired, or a budget was hit; consumers must treat it as denial

Evaluation captures one immutable scope snapshot and the active policy revisions once. Concurrent writes and publications cannot change a captured execution. JSON bodies are limited to 1 MiB and duplicate keys are rejected.

{"decision": "deny", "evaluation_status": "deny",
 "evidence_deadline": 1792173900,
 "policies": [{"policy": "Reviews", "status": "deny"}],
 "policy_documents": [{"revision": 3, "result": {…}}]}

Decisions also carry the runtime revision and, per document, the revision number and content digest.

Decision rules

All applicable bootstrap policies and active document sections in the scope combine into one decision.

Applicable policiesResult
No applicable policy, or an empty catalogDeny
All allowAllow
Any denyDeny
Any indeterminate — missing, stale, or expired evidence, or an unsupported external sectionIndeterminate (denies)
Evidence deadline passes before evaluation completesIndeterminate (denies)

Consumers must grant access only for an explicit decision: allow. Source: runtime_policy.rs, combined per scope by the evaluate endpoint in crates/ipe-server/src/runtime.rs.

Application responsibilities

  • Your application authenticates the caller and supplies the request data.
  • Your application controls who can change policies.
  • Your application handles evaluation errors.
  • Your application permits or blocks the action and records the result.

Current limits

  • Missing, stale, or expired facts yield indeterminate — negation cannot turn missing evidence into an allow.
  • Optional fact fields can be stored but are rejected at policy compilation until explicit option matching lands.
  • Storage is bounded: 10,000 keys per collection, 16 MiB encoded state, 1 MiB per value, 100 policies and 100 documents per scope.
  • The listener binds to loopback only; remote use requires a correctly configured local TLS proxy. There is no replication or joint transaction across the fact and policy stores.

Sources: runtime_facts.rs and runtime_policy.rs; the full list lives in RUNTIME_DATA.md.

Requirements
