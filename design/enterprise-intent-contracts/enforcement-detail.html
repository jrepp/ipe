JWT, request, and implementation notes

Sample signed JWT payload

{
  "iss": "https://identity.example",
  "aud": "release-service",
  "sub": "agent-01",
  "exp": 1800000000,
  "policy_endpoint": "https://policy.example/v1/scopes/acme/prod/evaluate"
}

The service verifies the signature with a configured issuer and algorithm. It checks the audience and expiry. It matches the custom claim to a trusted route for the request scope.

The claim identifies a configured evaluation endpoint. The service uses the registered destination. The engine evaluates all applicable policies in that scope. JWT claims · JWT security practices

Resource-Action-Request (RAR)

Illustrative input for a configured schema. The service authenticates separately from the agent JWT.

POST /v1/scopes/acme/prod/evaluate
{
  "input": {
    "resource": { "id": "release-42" },
    "action": { "operation": "Deploy" },
    "request": {
      "id": "request-42",
      "principal": { "id": "agent-01" }
    }
  }
}

The authenticated service sends the attested principal, resource, action, and context. The engine checks the service grant, exact tenant and environment binding, evaluation route, and input schema.

The principal matches the validated JWT subject. Trusted configuration binds the endpoint to acme/prod; request fields cannot change that binding.

The service applies a matching allow only within its usable validity. It records the applied decision separately from the release result.

Policy and fact reads

Policy publication appends an immutable revision. Activation selects the revisions available for evaluation. Each request captures the active revisions and a scoped fact snapshot.

Authorized publishers update facts separately. A fact retains its source, revision, and expiry. The engine reads local facts and rechecks the earliest required expiry before it returns allow.

Runtime status

The current runtime uses scoped bearer secrets. The JWT claim, route adapter, RAR exchange, and action gate show a proposal. The diagram makes no network requests.

The current runtime limits JSON bodies to 1 MiB. Its evaluation budget defaults to 10,000 steps. Captured reads do not establish a transaction across stores or a production performance target.
